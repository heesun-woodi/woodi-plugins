# PSR 가설 한 문장 — 조립·완성도 검증 규칙

— STEP 3(PSR 조립)에서 읽는다

> 출처: KB `04_hypothesis-psr.md` §2~5 / `04a_friday-backlog-workshop-guide.md` 4-3절 / `01_session-big-picture.md` 3절 / `hb-output-contract.md` §5.
> 기본 공식·상세 공식은 쓰지 않는다 — 이 스킬의 유일 공식은 **확장 공식**이다.

---

## 1. 확장 공식 (유일 공식)

```
"[영역/시점]에서 [문제]를 느끼는 [세그먼트]에게
 [솔루션 핵심가치]를 제공하면
 [지표]가 [Baseline]에서 [Target] 개선될 것이다"
```

이 문장을 읽은 제3자가 **추가 설명 없이 I/C/E를 매길 수 있어야 한다.** 못 매기면 요소가 빠진 것이다.

---

## 2. P/S/R 요소별 세부 구성과 재료 출처

| 요소 | 세부 구성 | 이 세션의 재료 출처 |
|---|---|---|
| **P — Problem** | [타겟 세그먼트] + [문제영역/지면/시점] + [고객이 느끼는 문제] | 입력 문제 리스트 — User Voice 문장 + BIAS 태그 |
| **S — Solution** | **[솔루션 핵심가치(소구점)]만** (형태는 문장에서 빼고 Variant로 — DEC-005) | STEP 1 솔루션 카드(H1) 3·4번 항목 |
| **R — Result** | [선행지표 1개] + [Baseline → **Target(필수)**] | `02a` 골트리 노드에서 선택 (아래 R 게이트 규칙 적용) |

**R이 선행지표여야 하는 이유 4가지**

| 이유 | 설명 |
|---|---|
| 인과 거리 | 선행지표는 솔루션 바로 다음 반응 — 인과 해석이 가능하다 |
| 샘플사이즈 | 최종 지표는 baseline이 낮아 필요 표본이 폭증하고 기간이 90일을 넘긴다 |
| 학습 해상도 | "노출됐는데 클릭이 안 됐다"는 다음 가설을 낳는다. "매출이 안 올랐다"는 학습이 남지 않는다 |
| 부작용 분리 | 선행지표 = Result, 최종 KPI = Guardrail — 역할을 나눠야 판정 규칙이 작동한다 |

### 설계사 가설의 PSR 요소 — 공식은 같고 주어만 바뀐다

고객 가설과 확장 공식은 동일하다. 세그먼트·영역·R의 자리에 설계사 관련 값이 들어간다.

| 요소 | 고객 가설 | 설계사 가설 (SP-N 계열) |
|---|---|---|
| 세그먼트 | 고객 세그먼트 (예: 상담방을 신규로 연 사용자) | 설계사 세그먼트 (예: 신규 배정 상담을 맡은 설계사, 하위 성과 그룹 설계사) |
| 영역/시점 | 고객이 보는 화면·시점 | 설계사가 일하는 화면·시점 (상담방 설계사 뷰, 어드민, 발송 직전) |
| 문제 | 입력 행의 고객 문제 문장 그대로 | 입력 행의 **설계사 문제 문장** 그대로 |
| 지표(R) | 고객 반응 지표 | **설계사 반응 지표** (아래 §3·§4 참조) |

---

## 3. R 게이트 규칙 — 골트리 노드에서 고른다

Result 지표를 새로 발명하지 않는다. `data/goal-tree-nodes.json`의 노드 목록에서 고른다.

| 상황 | 처리 |
|---|---|
| 노드 목록에 있고 `selectable: true` | 노드명을 **문자 그대로** R 칸에 쓴다 |
| `selectable: false` 노드 (진단 전용·축 최종 KPI) | 선택 불가 — 지표를 솔루션 쪽으로 당긴다 |
| 최종 KPI(계약·초회보험료·축 핵심 KPI)가 R로 올라올 때 | "지표가 솔루션에서 너무 멀다 — 솔루션 바로 다음 반응 지표로 당깁니다"를 멘트하고 교정 |
| 적합한 노드가 없을 때 | `[트리에 추가 필요 — Sprint 1 그루밍에서 논의]`를 R 칸에 메모로 남기고 진행한다 |
| 설계사 가설(SP-N)의 R 선택 | `user_type: 설계사` 노드를 우선 선택. 노드 `note`가 선행지표성을 부정하면 §4 R 적정성 3문항으로 재판단하고, 채택 시 사유를 코치 확인 항목으로 남긴다. 솔루션 직후 반응이 설계사 행동이므로 하류 고객 퍼널 지표는 R이 아닌 기대효과·Guardrail로 다룬다 |

> 노드명은 한 글자도 달라지면 안 된다. 문서뷰어 통합뷰가 문자 일치로 파싱한다.

---

## 4. R 적정성 3문항

아래 하나라도 걸리면 지표를 솔루션 쪽으로 당긴다.

1. Result가 최종 KPI(계약·초회보험료)가 아니라 **선행 반응 지표**인가
2. 솔루션과 지표 사이에 다른 사용자 행동이 **2개 이상** 끼어 있지 않은가, 또는 **다른 행위자가 끼어들지 않는가** (설계사 도구 → 고객 지표는 행위자가 바뀌므로 R을 설계사 반응까지 당긴다)
3. 이 지표는 **지금 측정되고 있는가** (불가하면 "세팅 의존성"으로 표시)

## 5. 고객 언어 판별 2규칙

**규칙 1** — 걸러야 할 것은 **주어가 지표(전환율·이탈률)·회사·"우리"인 문장**이다. 주어가 이 가설의 사용자(고객 또는 설계사)이고 서술어가 "~못 한다 / ~모른다 / ~느낀다"면 정상 문제 문장이다. `설계사는 ~ 못 한다`는 공급자 언어가 아니라 설계사 유형의 정상 문장이다 — 되돌리지 않는다.

**규칙 2** — 그 문장에서 솔루션이 자동으로 따라 나오면, 그것은 문제가 아니라 솔루션을 거꾸로 쓴 것이다.

### Bad / Good 대조

**❌ Bad 1 — R이 최종 KPI (B축 소재)**

> "상담방 첫 안내 메시지를 개인화하면 계약완료율이 5% 증가할 것이다"

P·S는 있지만 R이 최종 KPI다. 첫 메시지와 계약 사이에 정보 입력·견적·비교·다수 대화가 끼어 있어 인과를 특정할 수 없고, baseline이 낮아 기간도 감당 불가다.

**✅ Good 1 — 선행지표로 교정 (B축 소재)**

> "상담방에 처음 들어와 무엇을 얼마나 알려줘야 하는지 몰라 첫 답장을 미루는 사용자에게, 필요한 정보 항목 수와 예상 소요 시간을 첫 안내 메시지에서 먼저 알려주면, 상담 시작 → 정보 입력 완료율(견적 도달)이 [Baseline] → [Target] ([YY%]) 개선될 것이다"

| 요소 | 내용 |
|---|---|
| P | 상담방 첫 진입 사용자 / "얼마나 답해야 하는지 몰라 부담을 느낀다" |
| S | 정보 항목 수 + 소요 시간의 선(先)고지 / 첫 안내 메시지에 삽입 |
| R | 정보 입력 완료율(견적 도달) — 안내 메시지의 직접 반응. 계약완료율(최종 KPI)이 아님 |

---

**❌ Bad 2 — P·S는 구체적이나 R 지표가 솔루션에서 너무 멀다**

> "즉시배송 가능 지역이 배송지로 설정된 사용자가 15~16시에 로그인했을 경우 즉시배송 화면으로 진입시키면 장바구니 → 구매완료 전환율이 5% 증가할 것이다"

P·S는 매우 구체적이나 R이 잘못됐다. 솔루션(진입 화면 변경)과 지표(결제 완료) 사이에 상품 탐색·옵션 선택·장바구니가 끼어 있다. 교정: R을 **"상세페이지 → 장바구니 담기 전환율"**로 당긴다.

## 6. PSR 완성도 체크리스트 — 11항목 (스킬 셀프체크)

아래 모두 통과해야 H3 표에 문장을 확정한다. 미통과 항목은 `셀프체크` 열에 결손으로 기록한다.

- [ ] "P를 S로 바꾸면 R이 개선될 것이다" 구조인가
- [ ] 문제 주체가 명시되어 있는가 (주어가 이 가설의 사용자 — 고객 또는 설계사)
- [ ] 언제·어디서·무엇을 하다가 문제를 겪는지 구체적인가
- [ ] 공급자 언어가 아닌 고객 언어인가
- [ ] **S가 "고객이 무엇을 얻는가"(가치)로 끝나는가 — 형태(문구·UI·트리거)가 문장에 들어와 있지 않은가** (DEC-005)
- [ ] Result가 최종 KPI가 아니라 선행 반응 지표인가
- [ ] 솔루션과 지표 사이에 다른 사용자 행동이 끼어 있지 않은가
- [ ] **Target이 채워져 있고 설정 근거(벤치마크 / MDE / 내부 Gap)가 한 줄 붙어 있는가** (DEC-005)
- [ ] 대안 솔루션이 1개 이상 있는가 (문제당 솔루션 2개 이상)
- [ ] Solution Rationale·Counter Rationale이 각각 1개 이상 있는가
- [ ] **이 문장만 읽고 제3자가 I/C/E를 매길 수 있는가** — 그리고 소리 내어 읽어 자연스러운 한국어 한 문장인가

## 7. 제3자 ICE 테스트 — 사람이 페어 교차로 수행한다

**스킬은 이 테스트를 수행하지 않는다.** 안내만 한다.

블록 3 마지막 10분: **페어를 교차**한다. A축 페어가 B축 가설을, B축 페어가 A축 가설을 읽고 **설명 없이** I/C/E를 매긴다.

| 이 질문이 나오면 | 해당 요소가 비었다 |
|---|---|
| "누구를 대상으로?" | P의 세그먼트 |
| "어떻게 바꾼다는 거야?" | S의 형태 |
| "어느 지표?" | R |

질문이 나오면 해당 요소로 돌아가 문장을 교정한 뒤 다시 읽힌다.

## 8. Baseline 규칙

**골트리 노드에 실측 `current` 값이 있으면 그 값을 Baseline으로 쓴다** — 추정이 아니라 정본 데이터다. 후보가 복수이거나 척도가 다르면(예: "타율 78.9% · 지분 43.4%") 어느 값인지 참가자에게 확인하고, 못 정하면 아래 미확보 표기로 남긴다.

Baseline 수치가 없을 때 **추정하지 않는다.** 아래 표기를 그대로 쓴다.

```
[Baseline 미확보 — Sprint 1 실측]
```

- R 칸의 `Baseline → Target` 자리에 위 표기를 넣는다.
- **Target은 반드시 채운다** (DEC-005). 벤치마크 / MDE / 내부 Gap 중 하나로 잡고 어느 방법인지 한 줄 병기한다. Baseline 미확보면 **상대 개선율**로 적는다(예: `상대 +10%`).
- **추정치를 괄호로 넣는 것도 금지한다** — 근거 없는 수치는 쓰지 않는다.
- Baseline 실측은 Sprint 1 그루밍의 첫 번째 과제이며, 실측 전까지는 이 표기로 백로그에 등록한다.
- Target 근거를 참가자에게서도 못 얻으면 **관행값을 넣지 말고** `Target 미기재 — 코치 확인 필요`로 두고 **I·C를 공란 처리**한다(계약 §3-6 결손 경로).

> 전체 Uplift 시뮬레이션(증분 계약·초회보험료까지)은 Sprint 1 그루밍 소관이며 이 스킬의 범위 밖이다. **다만 Target 수치와 그 산출 근거는 이 스킬에서 반드시 확보한다** — 그것이 없으면 그루밍에서 uplift를 계산할 수 없고 Impact가 확정되지 않는다 (DEC-005).
