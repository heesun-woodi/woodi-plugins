## 2. 입력 규격 — 문제정의 리스트 정규화

### 2-1. 두 가지 사용자 유형 — 둘 다 정상 입력

이 세션의 입력은 **확정된 문제정의 리스트 행**이며, 문제의 **주어(사용자)가 누구인가**에 따라 두 유형으로 나뉩니다. **두 유형 모두 같은 절차(STEP 0~5)를 그대로 통과합니다.**

| 사용자 유형 | 문제 문장 주어 | 시트 위치 | 예 |
|---|---|---|---|
| **고객** | 고객 | `A축_문제정의` / `B축_문제정의` 탭의 **문제정의 리스트** 또는 **문제정의 (1) 고객 관점** | `PR-01`~ |
| **설계사** | 설계사(상담사) | `B축_문제정의` 탭의 **■ 문제정의 (2) 설계사 관점** | `SP-N1`~ |

**설계사 유형의 취지** (시트 원문): *"설계사는 [어떤 수단·정보]가 없어 [무엇을] 못 한다 · 고객 이탈을 결과로 붙이지 않는다 — 이렇게 쓰면 솔루션이 도구·시스템·템플릿 쪽으로 열린다."*

> **설계사는 이 가설의 사용자입니다.** 고객 문제의 원인이나 구현 제약이 아니라, **카톡으로 고객을 응대하는 설계사가 자기 도구·화면에서 겪는 문제** 그 자체가 P가 됩니다. 화면(STEP 0.5)은 설계사가 보는 화면, BIAS 단계는 설계사 여정의 실패 단계, PSR의 세그먼트는 설계사, R은 설계사 반응 지표입니다.

**공급자 언어 판별 (정정)**: 걸러야 하는 것은 **주어가 지표·회사·"우리"인 문장**입니다. `설계사는 ~ 못 한다`는 공급자 언어가 아니라 **설계사 유형의 정상 문제 문장**입니다. (구 규칙 "주어가 사람이면 고객 언어"는 오류 — `psr-guide.md`에서 정정.)

### 2-3. 행 단위 게이트 (세션 halt 아님)

붙여넣은 리스트에는 초안 행·미진단 행이 섞여 있는 것이 정상입니다. **무효 행은 해당 행만 제외**하고 사유를 고지한 뒤, 유효 행으로 진행합니다.

| 조건 | 처리 |
|---|---|
| `문제ID` 공란 | 행 제외 — "문제정의 미확정 행" 고지. 스킬이 ID를 만들지 않는다 |
| 문제 문장 공란 | 행 제외 |
| 문제 문장이 **상태 기록**일 때 (`⚠ 미진단 …`, `[폐기] …` 등) | 행 제외 — 문장이 채워져 있어도 사용자 주어 문제 문장이 아니다 |
| BIAS 단계가 `미판정`·`미진단` | 행 제외 — 전술 매핑이 성립하지 않는다 |
| 유효 행이 **0건** | 그때만 세션 중단 → `cro-problem-definition` 스킬 또는 코치 안내 |

### 2-4. 설계사 행의 BIAS 단계 — 재판별 필요

시트 설계사 섹션의 BIAS 단계 자리는 열 이름이 **`관련 고객 문제 단계`**입니다. 이 값은 **짝지어진 고객 문제의 단계**이지 설계사 문제 자체의 단계가 아닙니다. 그대로 쓰면 전술이 엉뚱한 문제 기준으로 선정됩니다.

- 설계사 행은 **설계사 여정 기준으로 단계를 재판별**합니다 (설계사도 자기 도구 앞에서 주목→이해→행동→기억을 거칩니다). 판별 질문은 `planner-problem-guide.md`.
- 시트 원값은 `관련 고객 문제 단계`로 따로 보존해 H5b에 병기합니다.

### 2-5. Impact 결손 처리

- Impact가 비어 있으면 스킬이 값을 만들지 않습니다. **비어 있는 항목만** 참가자에게 요청해(세 점수를 일괄 요구하지 않음) 산식대로 계산하고 **`추정` 표시**를 남깁니다.
- 세 요소 중 하나라도 확보 불가면(측정 자체가 불가능한 경우 포함) **Impact는 공란 + `코치 확인 필요`**. 추정치로 채우지 않습니다.
- 이 경우 **ICE 합·QuickWin이 산출되지 않습니다** — §3-6·§3-7의 결손 표기 규칙을 따릅니다.

### 2-6. `근거유형` 어휘 대응 — 기계 변환 금지

시트 어휘(`관측` / `정성` / `관측+정성` / `정성(설문)+관측` 등)와 백로그 필드(`실측` / `합성` / `혼합`)는 **같은 축이 아닙니다.** 시트 값은 진단 근거의 관측/정성 성격이고, 백로그 값은 **합성 인터뷰(AI 생성 응답) 포함 여부**를 가립니다 — 이 값이 Confidence 상한 1~3을 발동시키므로 오변환이 점수를 왜곡합니다.

**반드시 참가자에게 직접 묻습니다**: *"이 문제의 정성 근거가 실제 설문·인터뷰·전사인가요, 아니면 합성 인터뷰(AI 생성)가 섞여 있나요?"*

| 답변 | 백로그 `근거 유형` |
|---|---|
| 실제 설문·전사·관측만 | `실측` |
| 합성 인터뷰만 | `합성` (→ C 상한 1~3) |
| 실측 + 합성 | `혼합` |

### 2-7. 문제ID 접두어

- 시트 표기는 축 코드가 없을 수 있습니다(`PR-01`). 저장소 표기는 `PR-{A|B}-nn`이며 **둘은 같은 것**으로 봅니다 — 산출물에는 저장소 표기로 적습니다.
- `SP-N1`처럼 **알려지지 않은 접두어**는 임의 해석하지 않고 무엇인지 한 번 확인합니다(설계사 섹션이면 사용자 유형 = 설계사).
- 선언한 축과 다른 축 접두어가 섞이면 경고합니다.

### 2-8. BIAS 체계 버전 확인

저장소 정본은 **27항목**(DEC-003)이지만, 워크숍 시트가 **구 체계 15항목 기준**으로 고정돼 있을 수 있습니다(A축 시트 2026-08-12 결정). 같은 항목ID가 체계에 따라 다른 항목을 가리키므로(15항목 `B4` = 인지 부하 최소화 / 27항목 `B4` = 선택지 과부하 방지) 조용한 오염이 발생합니다.

- STEP 0에서 **한 번 확인**합니다: *"이 리스트의 BIAS 판정은 27항목 기준인가요, 구 체계 15항목 기준인가요?"*
- 15항목 기준이면 H5b의 `BIAS 단계` 값에 **`(15항목 기준)`을 병기**합니다.

- **문제 문장이 좁아 두 번째 솔루션이 필연적으로 Variant가 되는 경우**: "문제당 2개 이상"이 "Variant 걷어내기"보다 우선하지 않습니다. 다른 접근을 찾되, 정말 없으면 참가자에게 다른 지면·다른 시점의 접근을 요청하고, 그래도 없으면 1개로 두고 사유를 기록합니다.

### 3-6. 결손 표기 규칙 (신규 — v1.1)

I 공란(Impact 미확보)과 E 공란(담당자 미답)은 이 계약이 명시적으로 허용하는 **정규 경로**입니다. **v1.3부터 Target 미기재로 인한 I·C 공란이 여기에 추가됩니다**(§7-2·§7-4a) — 표기 방식은 동일합니다. 그 결과를 아래와 같이 표기합니다.

| 위치 | 표기 |
|---|---|
| H4 `ICE 합` | `미산출` |
| H4 `QuickWin` | `판정 불가` |
| **H5a `ICE 합`** | **`-`** (숫자 파싱을 깨뜨리지 않기 위해 문자열을 넣지 않는다) |
| **H5a `QuickWin`** | **`-`** |
| H5b `계산` 블록 | `ICE 총점: {I} + {C} + (E 미확보) = **미산출 / 30**` · `QuickWin 여부: **판정 불가** — {결손 사유}` |

- H5b `계산` 블록에 **무엇이 왜 비었는지**를 한 줄로 적습니다 (예: `E 미확보 — 담당자가 개발팀 확인 후 회신 예정`).
- 결손 가설도 백로그에 올립니다. 점수가 없다는 사실 자체가 그루밍 착수 목록의 첫 줄입니다.
- ⚠️ 확인필요 — H5a에서 `-`가 "값 없음"으로 파싱되는지는 문서뷰어 구현에 달려 있습니다. 통합뷰가 깨지면 코치가 표기를 재지정합니다.

**메타데이터**

**PSR 전문 + I·C·E**
- PSR 전문: "{확장 공식 한 문장}"
- Impact(I): **{n}** — {이관/재계산 근거} (결손이면 `(공란)` + 사유)
- BIAS 단계: {Block/Interpret/Act/Store + 항목ID} {(15항목 기준) 병기 시}

- 근거 유형: {실측/합성/혼합}

**계산**
- ICE 총점: {I} + {C} + {E} = **{합} / 30**  (결손 시 §3-6)
- QuickWin 여부: **{예/-/판정 불가}** — {판정 경로}

**솔루션 카드**

## 4. 표 출력 규칙

1. H1~H5a는 **마크다운 표로 대화에 렌더해** 출력합니다. 코드블록에 넣지 않습니다.
2. **유일한 예외 — H5b는 코드블록(raw markdown)으로 출력합니다.** 복사 대상이 시트 셀이 아니라 repo `.md` 파일이므로 원문 마크다운이 필요합니다.
3. 표 바로 위 또는 아래에 착지 안내 한 줄.
4. 열 이름·순서는 3절과 문자 단위로 동일. 임의 추가·삭제·재배열 금지.
5. 셀 안 줄바꿈 금지 (콤마·슬래시·`→` 사용). PSR 전문도 한 문장.
6. 셀 첫 글자에 `=`·`+` 금지 (시트 수식 오인).

## 5. 문장·서술 형식 (정본)

**PSR 확장 공식** — 이 공식만 사용합니다. 사용자 유형에 따라 세그먼트 자리가 달라질 뿐 구조는 같습니다.

```
"[영역/시점]에서 [문제]를 느끼는 [세그먼트]에게
 [솔루션 핵심가치]를 제공하면
 [지표]가 [Baseline]에서 [Target] 개선될 것이다"
```

> **[솔루션 형태]는 이 문장에 넣지 않습니다** (DEC-005, 2026-08-18). 형태는 Variant 구성으로 내려갑니다 — §5-2.
> **[Target]은 반드시 채웁니다.** `[YY%]` 자리 비워두기는 더 이상 허용되지 않습니다 — §7-7.

| 요소 | 고객 가설 | 설계사 가설 |
|---|---|---|
| 세그먼트 | 고객 세그먼트 (예: 상담방을 신규로 연 사용자) | **설계사 세그먼트** (예: 신규 배정 상담을 맡은 설계사, 하위 성과 그룹 설계사) |
| 영역/시점 | 고객이 보는 화면·시점 | **설계사가 일하는 화면·시점** (상담방 설계사 뷰, 어드민, 발송 직전) |
| 문제 | 입력 행의 고객 문제 문장 | 입력 행의 **설계사 문제 문장** 그대로 |
| 지표(R) | 고객 반응 지표 | **설계사 반응 지표** (§7-7) |

- **완결 기준**: 제3자가 이 문장만 읽고 추가 설명 없이 I/C/E를 매길 수 있어야 합니다.
- **솔루션 서술**: **"고객이 무엇을 얻는가"까지만.** "개선한다"처럼 값이 없는 서술은 금지하되, 형태(문구·UI·트리거 시점)로 내려가서도 안 됩니다 — 그건 Variant 자리입니다(§5-2).
- **Counter Rationale 형식**: `{실패 시나리오 한 줄} → {무너질 지표}를 Guardrail 후보로 관찰`. "효과 없을 수 있다" 수준은 반려.
- **사용자 언어**: P의 문제는 입력 리스트의 문장을 그대로 씁니다. 주어가 **지표·회사·"우리"**인 문장("~률이 낮다")이 오면 문제정의로 되돌립니다. **설계사 주어는 되돌리지 않습니다** (§2-1).

### 5-1. 문장 가독성 (신규 — v1.3)

PSR 전문은 **사람이 소리 내어 읽을 수 있는 완성된 한국어 한 문장**이어야 합니다. 슬롯이 다 차 있어도 아래에 해당하면 다듬어 다시 씁니다.

| 금지 | 이유 | 처리 |
|---|---|---|
| 앞머리 가설명 태그 (`[요소 다이어트]`, `[상령일 D-day]` 등) | 문장의 일부처럼 읽혀 P1(영역)과 섞인다 | 태그는 **가설명 필드**로 분리, 문장에서 제거 |
| 대괄호 템플릿 잔존 (`[…]에서 […]를 느끼고 있는 […] 사용자에게`) | 빈칸 채우기 흔적이 남아 문장으로 안 읽힌다 | 대괄호를 걷고 조사·어미를 이어 붙인다 |
| 공급자 시점 화면 묘사 (`화면이 예시 견적만 보여줘`) | 고객이 인지하지 못하는 사실이 문장에 들어간다 | 고객이 **느끼는 것**으로 바꾼다 (`이 점검이 내 걸 보고 만든 건지 광고인지 구분이 안 되어`) |
| 영역·세그먼트 중복 (`점검신청 화면에서 … 점검신청 화면 도달 고객에게`) | 같은 말이 두 번 나온다 | 앞에 영역이 있으면 세그먼트는 `고객에게`로 줄인다 |

### 5-2. Solution ≠ Variant — 무엇이 문장에 남고 무엇이 내려가나

**같은 가치를 여러 형태로 구현할 수 있고, 어느 형태가 이기는지를 보는 것이 실험입니다.** 형태를 문장에 박으면 그 비교가 사라집니다.

| | PSR 문장 | Variant 구성 (실험 설계) |
|---|---|---|
| 들어가는 것 | **가치** — 고객이 무엇을 얻는가 | **형태** — 어느 지면의 무엇을, 어떤 트리거로, 어떤 UI로 |
| 예 | *"내 보험에서 무엇이 비어 있는지 알려준다면"* | A: 「지금 내 보험, 괜찮은 걸까?」 섹션을 보장 부족 6개 진단으로 교체 / B: CTA 위 슬롯에 부족 항목 2개만 요약 |

- H1 솔루션 카드의 `솔루션(How)` 열은 **그대로 유지**합니다 — 형태를 버리는 게 아니라, **문장에서 Variant 열로 자리를 옮기는 것**입니다.
- 형태 후보가 1개뿐이면 그대로 두되, `Variant 후보 1개 — 그루밍에서 대안 형태 추가 필요`를 남깁니다.

## 7. 공식 · 판정 규칙 (정본 — 위반 금지)

```
ICE = Impact + Confidence + Ease     (각 1~10점, 합산, 총점 최대 30점)

QuickWin = ICE ≥ 21   또는   (ICE ≥ 15 AND Ease ≥ 8)
```

**7-1. 곱셈식·평균식은 어떤 형태로도 출력하지 않습니다.** 과거 문서에 다른 표기가 있으면 I/C/E 원 점수만 살려 합산으로 재계산합니다.

**7-2. I = 입력 리스트의 Impact 점수 이관. 재계산 금지.** 참가자가 개인 스코어링에서 다른 I를 주더라도 이관값을 대체하지 않습니다(본인 점수는 분산 기록란으로).

- **단, Target이 없으면 I는 확정되지 않습니다** (DEC-005). 이관값은 **문제**의 크기이고, 가설의 Impact는 **이 솔루션이 그 문제를 얼마나 되돌리는가**까지 가야 값이 섭니다. 그 계산이 `Target → 선행지표 증분 → 최종 KPI uplift`이고, Target이 비면 uplift 시뮬레이션이 성립하지 않습니다.
- 처리: Target 미기재 행은 **I를 `(잠정 이관값)`으로 표시**하고 `Target 미기재 — uplift 미산출`을 I 근거에 남깁니다. Target이 채워지면 uplift를 계산해 I를 확정합니다.

**7-3. BIAS 가중은 한 번만, 심각도 경로로만.** 문제정의에서 이미 정성 심각도에 Block +2 / Interpret +1이 반영됐으면 I에서 아무것도 더하지 않습니다. 불명확하면 **정성 심각도에 +2/+1 → 10점 캡 → `/3` 재계산**하고 그 사실을 I 근거에 적습니다. **Impact 총점에 직접 가산하지 않습니다** (심각도 경로는 ÷3을 거치므로 +0.67).
- 시트가 "가중은 BIAS·CRO 어느 쪽에서 걸렸든 적용한다"처럼 더 넓은 규칙을 쓰고 있으면, **상류에서 이미 적용된 값을 그대로 이관**하고 재판단하지 않습니다.

**7-4. C 앵커 4밴드**

| 점수 | 기준 |
|:-:|---|
| 10 | 검증된 자사 데이터 + 경쟁사 대부분 채택 + 성공 경험 |
| 7~9 | 경쟁사 벤치마크 강함, 신뢰할 만한 레퍼런스 다수 (확인된 사례 3곳 이상) |
| 4~6 | 경쟁사 1~2곳 채택, 또는 케이스 스터디·**행동경제학 이론 수준** |
| 1~3 | 근거 부족·직관 수준 — **합성 인터뷰만 있는 경우는 반드시 여기** |

- **적용한 전술의 행동경제학 원리를 명시할 수 있으면 4~6 밴드 하단**입니다. 외부 사례를 못 찾았다는 이유만으로 1~3으로 내리지 않습니다. 1~3은 **합성-only, 직관, 원리조차 제시 못 하는 경우**입니다.
- **합성 상한(하드)**: 근거가 합성 인터뷰뿐이면 C는 1~3을 넘지 않습니다.
- **교정 트리거**: 참가자 점수가 **해당 근거의 밴드 상한을 넘으면** 교정합니다(고정 임계 7이 아님).

**7-4a. Target 타당성은 C에 반영합니다** (신규 — DEC-005)

C는 "이 솔루션이 통할 것 같은가"만이 아니라 **"이 Target이 말이 되는 수치인가"**까지 담습니다. 근거가 같아도 Target이 다르면 C가 달라집니다.

| Target의 성격 | C 반영 |
|---|---|
| 벤치마크·자사 실측·MDE 등 **산출 근거가 붙은 수치** | 밴드 내 **상향** |
| 근거 없이 관행으로 잡은 수치 (예: 이유 없는 "10%") | 밴드 내 **하향** |
| 근거 대비 **과한 수치** (예: 이론 근거만 있는데 상대 +50%) | 밴드 자체를 **한 단계 내림** |
| **Target 미기재** | **C 공란 + `Target 미기재 — 타당성 판단 불가`** |

- Target 산출 근거는 `C 근거` 한 줄에 함께 적습니다 (예: `자사 실측 패턴 + Target은 벤치마크 82% 대비 절반 회수 = 상대 +5%`).
- 이 항목은 **밴드를 새로 만들지 않습니다** — §7-4의 4밴드 안에서 위치를 조정하는 규칙입니다.

**7-5. 출처 확인 3단계**

| 상태 | 표기 | C 밴드 반영 |
|---|---|---|
| 페이지를 실제로 열어 확인 | `URL + 확인일` | 정상 반영 |
| 검색 결과 요약에만 등장, 원문 미확인 | `2차 인용 — 원문 미확인` | 반영하되 **밴드 하단** |
| 찾지 못함 | `확인되지 않음` | 미반영 |

존재하지 않는 URL·수치·사례를 만들지 않습니다.

**7-6. Guardrail ≠ Result.** Counter Rationale의 무너질 지표가 그 가설의 R과 같으면, **한 단계 뒤 지표**로 밀어 지목합니다(예: R이 진입률이면 Guardrail은 완료율). 측정 불가 노드를 Guardrail로 지목할 때는 `세팅 의존성`을 병기합니다.

**7-7. R(Result) 선택 규칙**

- 골트리 노드에서만 고르고 **문자 일치**로 씁니다. `selectable: false` 노드는 선택 불가.
- **설계사 가설의 R은 설계사 반응 지표**입니다 — 솔루션 바로 다음에 일어나는 반응이 설계사의 행동이기 때문입니다. 하류 고객 퍼널 지표는 `기대효과` 서술과 Guardrail로 다룹니다.
- 노드의 `note`가 선행지표성을 부정하면(예: "선행지표 아닌 주력 통로") R 적정성 3문항으로 재판단하고, 채택하면 사유를 코치 확인 항목으로 남깁니다.
- 적합한 노드가 없으면 `[트리에 추가 필요 — Sprint 1 그루밍에서 논의]`.
- **Baseline**: 노드에 실측 `current`가 있으면 **그 값을 Baseline으로 씁니다**(추정이 아니라 정본 데이터). 후보가 복수이거나 척도가 다르면 어느 값인지 참가자에게 확인하고, 못 정하면 `[Baseline 미확보 — Sprint 1 실측]`.
- **Target은 필수입니다** (DEC-005 — v1.2까지의 "근거가 없으면 미확보 표기"를 대체). `[YY%]`를 빈칸으로 남기지 않습니다. Target이 없으면 uplift가 계산되지 않아 **I가 확정되지 않고**(§7-2), Target 타당성을 볼 수 없어 **C도 매겨지지 않습니다**(§7-4a).
  - 설정 방법 3가지 중 하나를 골라 쓰고 **어느 방법인지 한 줄로 병기**합니다: ① **벤치마크** — 목표 전환율 대비 Gap의 일부를 회수 ② **MDE** — 실험이 검출 가능한 최소 효과 ③ **내부 Gap** — 자사 최고 구간·상위 그룹 수준까지.
  - Baseline이 미확보면 절대값 대신 **상대 개선율**로 씁니다 (예: `[Baseline 미확보] → 상대 +10%`).
  - 근거를 정말 못 만들면 **관행값을 넣지 말고** 참가자에게 묻습니다. 그래도 안 나오면 `Target 미기재 — 코치 확인 필요`로 두고 **I·C를 공란 처리**합니다(§3-6 결손 경로). 추정치를 몰래 채우지 않습니다.

**7-8. Ease는 스킬이 추정하지 않습니다.** 참가자에게 워킹데이 기준으로 묻고(개발·인프라·승인·법무·운영 합의 포함), `E 근거` 첫머리에 `(잠정)`을 강제합니다. 답을 못 받으면 공란 + `코치 확인 필요`(§3-6).

**7-9. 스킬 점수의 지위**: 스킬의 I/C/E는 "그루밍 전 1차(잠정)" **보조 참고값**입니다. 팀 점수가 되지 않으며, 개인 스코어링 → 분산 확인 → 조정 토론(평균 금지)이 정본 절차입니다.

**7-10. 프로젝트별 근거 사용 제약**: 리스트나 시트에 근거 사용 금지 규칙(예: "과거 실험 결과를 어느 방향으로도 인용하지 않는다")이나 해결안 제약(예: "톤을 문제로 읽지 말 것")이 명시돼 있으면 **스킬 기본 절차보다 우선**합니다. STEP 0에서 한 번 확인하고 전 STEP에 적용합니다.

## 9. 완료 판정 체크 (8항목) 및 종료 경로

1. PSR 가설(목표: 축당 3~4개)이 확장 공식 한 문장으로 쓰였는가
2. 모든 가설의 R이 골트리 노드에서 선택되었고 선행 반응 지표인가
3. 모든 문제에 솔루션이 2개 이상인가 (§3-1 예외 사유 기록 시 제외)
4. 모든 가설에 Rationale 1개 이상 + Counter Rationale 1개 이상이 있는가
5. 제3자 ICE 테스트(교차 리뷰)를 사람이 수행했는가 — **비동기 단독 모드에서는 "다음 세션 교차 리뷰 예약"으로 대체 가능**
6. ICE가 합산식(최대 30)으로 계산되고 QuickWin 판정이 붙었는가 — **결손 표기(§3-6)가 정확하면 충족으로 본다**
7. 모든 행이 "그루밍 전 1차(잠정)"이고 `E 근거` 첫머리에 `(잠정)`이 적혔는가
8. 분산 기록란(사람 기록)을 남기도록 안내했는가

**종료 경로 (신규 — v1.1)**: N 항목이 있으면 해당 STEP으로 돌아갑니다. 단 **세션 안에서 해소가 불가능한 원인**(로깅 부재, 개발팀 부재, 페어 부재, 화면 미확보 등)이면 무한 루프에 빠지지 않고 **`코치 확인 필요` 목록으로 정리해 세션을 종료**합니다. 목록에는 항목·원인·해소 조건·담당을 한 줄씩 적습니다.
