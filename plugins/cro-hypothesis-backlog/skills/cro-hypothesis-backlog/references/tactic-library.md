## 1. 12전술 라이브러리

BIAS 4단계별 정렬. 문제의 BIAS 태그와 같은 단계의 전술을 1순위로 검토한다.
이 표를 인쇄해서 책상에 두고 쓴다. 화면 공유로만 보여주면 안 본다.

| 단계 | # | 전술 | 한 줄 정의 | 적용 예 |
|---|:-:|---|---|---|
| Block | ① | Cocktail Party Effect | 이름·지역·상황을 직접 언급해 "내 이야기"로 인식시켜 주의를 끈다 | 유입 검색어를 히어로 헤드라인에 반영("'{검색어}' 찾으셨나요?"), 세그먼트 호칭("6개월 이상 사용 중이신 분께") |
| Block | ② | Pattern Interrupt | 예상 밖의 대비·질문형으로 무시 본능(배너 블라인드니스)을 깬다 | 배너처럼 생긴 영역을 본문 인라인 카드로 전환, 정적 이미지 → 짧은 루프 모션 |
| Block | ③ | Curiosity Gap | 정보 공백을 만들어 읽게 만든다. **답을 같은 화면에 둬야** 낚시가 아니다 | "왜 3명 중 1명은 첫 주문에서 멈출까?", "이 3가지를 놓치면 할인이 사라집니다" |
| Block | ④ | Visual Cueing | 시선 방향·화살표·여백 대비로 CTA에 시선을 강제 이동시킨다 | 모델의 시선을 CTA 쪽으로 향하게 크롭, CTA 직전에 방향 아이콘 배치, CTA 주변 여백 확대 |
| Interpret | ⑤ | Framing Effect | "비용"을 더 작은 단위나 다른 범주로 재정의해 저항감을 낮춘다 | "월 3만원" → "하루 1,000원(커피 한 잔 값)", "구독료" → "1회 상담 비용보다 저렴" |
| Interpret | ⑥ | Labor Illusion | 처리 과정을 시각화해 "나를 위해 일하는 중"으로 느끼게 한다 | "최저가 47곳 비교 중…" 진행 애니메이션, 추천 알고리즘 계산 단계 노출 |
| Interpret | ⑦ | Loss Aversion | 얻는 것보다 "지금 떠나면 잃는 것"을 강조한다 | "장바구니 쿠폰이 3시간 뒤 소멸됩니다", "지금 나가면 적용된 할인 12,000원이 사라져요" |
| Act | ⑧ | Decoy Effect | 매력 없는 옵션을 옆에 둬 팔고 싶은 옵션을 돋보이게 한다 | 3개 요금제 중 중간 옵션을 비합리적으로 설계해 상위 옵션을 합리적으로 보이게 |
| Act | ⑨ | Social Proof | 타인의 행동을 구체적 숫자로 보여 확신을 준다 | "현재 1,203명이 보는 중", "재구매율 1위", "250+ 기업이 함께 성장했습니다" |
| Act | ⑩ | Goal Gradient | 진행바를 일부 채워진 상태로 제시해 완주율을 높인다 | 5단계 가입 폼에서 1단계 진입 시 이미 20% 채워진 진행바, 스탬프 10개 중 2개 선지급 |
| Store | ⑪ | Peak-End Rule | 경험의 정점과 마지막에 가장 큰 시각적 보상을 배치한다 | 결제 완료 화면의 축하 애니메이션, 제출 완료 시 개인화된 다음 액션 카드 |
| Store | ⑫ | Cognitive Dissonance 해소 | 선택을 지지하는 문구로 행동 후 불안을 제거한다 | "합리적인 선택을 하셨어요 — 같은 조건 대비 18% 절약", 주문 완료 후 재구매율 제시 |

**전술 조합**: 하나의 솔루션에 2~3개 전술을 겹쳐 쓰는 것은 허용된다. 다만 어느 전술이 효과를 냈는지 분리 측정이 불가능해진다. 지표 개선이 급하면 조합, 전술 자체를 학습하려면 단일로 간다. 조합했을 때는 Rationale에 "전술 분리 미검증"을 명시한다.

**Curiosity Gap 주의**: "무시 본능을 깬다"(Pattern Interrupt)와 "정보 공백으로 읽게 만든다"(Curiosity Gap)는 작동 원리가 다르므로 별도 전술로 유지한다. 답이 같은 화면에 없으면 클릭률은 오르고 이탈률도 오른다 — Store 단계가 손상된다.

**이 라이브러리를 쓰는 이점 세 가지**:
- **발산의 품질 하한선 보장** — 담당자 개인의 아이디어 총량에 의존하지 않는다.
- **Rationale이 자동으로 따라온다** — 전술 자체가 검증된 행동경제학 원리이므로 ICE의 Confidence 근거로 바로 쓰인다.
- **실험 간 학습이 누적된다** — "우리 서비스에서 이 전술은 잘 먹히고 저 전술은 안 먹힌다"는 조직 자산이 쌓인다.

## 2. 문제 유형 → 전술 매핑

1순위가 리소스·브랜드 제약으로 막히면 2순위로 내려간다.

| 단계 | 문제 유형 | 1순위 | 2순위 |
|---|---|---|---|
| Block | 가치 제안이 불명확함 | Pattern Interrupt | Visual Cueing |
| Block | 정보가 무시당함 | Cocktail Party Effect | Pattern Interrupt |
| Block | 본문을 읽지 않고 이탈 | Curiosity Gap | Pattern Interrupt |
| Block | 인지 과부하 | Visual Cueing | — |
| Block | CTA가 눈에 안 띔 | Visual Cueing | Pattern Interrupt |
| Interpret | 가격 저항 | Framing Effect | Loss Aversion |
| Interpret | 혜택 이해 부족 | Framing Effect | Labor Illusion |
| Interpret | 가치 인식 부족 | Labor Illusion | Framing Effect |
| Interpret | 손실 인식 부족 | Loss Aversion | Framing Effect |
| Act | 결정 미룸/망설임 | Social Proof | Goal Gradient |
| Act | 선택 장애 | Decoy Effect | Social Proof |
| Act | 신뢰 부족 | Social Proof | — |
| Act | 진행 포기 | Goal Gradient | Social Proof |
| Act | 긴급성 부재 | Loss Aversion | Social Proof |
| Store | 경험 기억 안 남음 | Peak-End Rule | — |
| Store | 구매 후 불안 | Cognitive Dissonance 해소 | Peak-End Rule |
| Store | 재방문 동기 없음 | Peak-End Rule | Cognitive Dissonance 해소 |

> **"긴급성 부재"만 예외입니다.** Act 단계 문제인데 1순위가 Interpret 전술(Loss Aversion)입니다 — "지금 안 해도 된다"는 판단은 Act 단계에서 드러나지만 원인이 Interpret(손실 인식 부족)에 있기 때문에, 이 한 줄만 Interpret 전술을 차용합니다. 원칙 1(단계 일치)의 예외로 명시하고, 다른 행에는 적용하지 않습니다.

> 브랜드 가이드나 리소스 제약으로 1순위 전술이 막히는 경우가 흔합니다. 그때는 2순위로 내려갑니다. **전술이 막힌 것이지 문제가 사라진 것은 아닙니다.**

## 3. 단계 매칭 규칙

**원칙: 문제의 BIAS 단계 = 전술의 BIAS 단계를 1순위로 검토한다.**

아이디어 회의에서 떠오른 순서대로 적는 게 아니라, "이 문제는 Block 실패다 → Block 전술 4종 중에서 고른다"로 좁힌다.

- 먼저 문제의 BIAS 태그를 확인하고, 매핑 테이블에서 1순위 전술을 고른 뒤 "문제 단계와 전술 단계가 일치하는지" 검증한다.
- **Block 문제에 Social Proof를 붙이는 것이 가장 흔한 실수다.** 교정 멘트: **"안 보이는 것에 내용을 더해도 안 보입니다."** 이 조합은 그루밍 리뷰에서 Fail 처리된다.
- 1순위 전술이 막히면 2순위로 내려간다. **전술이 막힌 것이지 문제가 사라진 것은 아닙니다.**
- 매핑 테이블에 없는 문제 유형은 BIAS 단계를 먼저 확인하고 같은 단계 전술 중 작동 원리가 가장 가까운 것을 고른다.
- "긴급성 부재" 한 행만 단계 불일치 예외다. 다른 행에 이 예외를 확장 적용하지 않는다.

## 4. 솔루션 발산 원칙

### 원칙 1 — 문제당 솔루션 2개 이상

첫 아이디어가 최선일 확률은 낮다. 솔루션이 1개뿐이면 그 안이 Ease에서 막힐 때 문제 자체가 백로그에서 사라진다. 문제를 검증하는 과정에서 떠오른 대안을 반드시 함께 적는다. 대안이 있어야 ICE 비교가 되고, 첫 안이 막혔을 때 문제를 살릴 수 있다.

### 원칙 2 — "개선한다" 금지. How(UI 형태·문구·트리거 시점)까지

솔루션은 "어떻게 바꾸는가"가 명확해야 한다.

- 나쁜 예: "상담방 첫 메시지를 개선한다"
- 좋은 예: "상담방 오픈 직후 발송하는 첫 메시지에 고객 이름·보장 공백 항목을 언급하는 개인화 문구를 삽입한다 (트리거: 상담방 오픈 이벤트, 형태: 카카오 텍스트 메시지)"

"개선한다"로 끝나는 솔루션은 코치 개입 대상이다. 교정 멘트: "어떻게(How)까지 적어주세요 — UI 형태, 문구, 트리거 시점."

### 원칙 3 — Solution ≠ Variant

솔루션은 "어떤 접근으로 해결할 것인가", Variant는 "그 접근을 어떤 형태로 표현할 것인가"다. 이 둘을 섞으면 실험 결과 해석이 불가능해진다.

| 층위 | 질문 | 예시 |
|---|---|---|
| **Solution** | 이 문제를 어떤 접근으로 해결할 것인가 | 상담방 첫 메시지를 개인화 문구로 교체 |
| **Variant** | 그 솔루션을 어떤 형태로 표현할 것인가 | 문구안 A (이름+보장 공백) / 문구안 B (이름+다음 단계 안내) |

Variant 걷어내기 기준: 같은 솔루션의 문구·이미지·위치 변형 여러 개를 나열하고 있다면, 그것은 솔루션이 아니라 Variant다. 이날(STEP 1)은 솔루션만 만든다. 단일 축 변형·Control 대조표는 Sprint 1 실험 설계서에서 만든다.

## 5. MVP 축소 4문항

솔루션 발산 직후 이 4문항으로 훑는다. Variant가 개발 의존적이면 Ease가 떨어져 스프린트에 못 탄다.

1. 이 안은 고객의 어떤 구체적 행동(Action)을 유도하는가
2. 이 기능이 고객의 어떤 Pain Point를 해결하는가
3. 검증에 반드시 필요한(Must have) 요소는 무엇이고, 빼도(Won't have) 검증되는 요소는 무엇인가
4. 개발팀 도움 없이(혹은 최소화하여) 실험 툴로 구현 가능한가

> 3번에서 걸러지는 것이 대체로 "디자인 욕심"입니다. 빼도 가설이 검증되면 뺍니다.

## 6. 해빗팩토리 맥락 주의

이 전술 라이브러리는 범용 정의로 작성돼 있다. 해빗팩토리 두 축은 UI 환경이 달라 같은 전술이라도 구현 형태가 다르다.

**A축 (보험분석 → 점검신청 → 상담방 오픈)** — 앱 화면이 주 지면이다. 전술 적용 형태는 화면 레이아웃(배너·카드·CTA 버튼), 헤드라인 문구, 시선 유도 요소, 진행바 등 일반적인 온사이트 패턴을 따른다. Visual Cueing(시선 방향·여백 대비), Pattern Interrupt(이미지·색상 대비), Goal Gradient(단계 진행바) 등은 앱 화면에서 그대로 구현 가능하다.

**B축 (상담방 오픈 → 상담 시작 → 정보 입력 → 견적 → 계약)** — 카카오톡 상담방이 주 지면이다. UI 요소가 메시지·버튼(카카오 퀵리플라이·버튼형 메시지)·카드형 메시지로 한정된다. 같은 전술이라도 구현 형태를 번역해야 한다.

| 전술 | A축 구현 형태 | B축 구현 형태 |
|---|---|---|
| Goal Gradient | 단계별 진행바 (% 표시) | "3가지 중 1가지 완료했어요" 텍스트 안내 메시지 |
| Social Proof | 리뷰 수·가입자 수 배지 | "이번 달 ○○명이 이 단계를 완료했어요" 메시지 카드 |
| Curiosity Gap | 헤드라인 질문형 문구 | "결과를 먼저 보고 싶으신가요?" 버튼 선택지 |
| Visual Cueing | 화살표·시선 방향·여백 | 굵은 텍스트·이모지·버튼 위치 순서로 시선 유도 |

B축 솔루션을 서술할 때 "배너·팝업·이미지 CTA"를 기본값으로 쓰면 구현 불가 가능성이 높다. **솔루션 How에 "메시지·버튼·카드 형태로 어떻게 구현할 것인가"를 명시한다.**

## 7. 흔한 실수 + 교정

| 실수 | 교정 |
|---|---|
| Block 문제에 Social Proof를 붙임 | Block 문제(안 보임)에 Social Proof(신뢰 보강)를 붙이는 사례가 가장 많다. **"안 보이는 것에 내용을 더해도 안 보입니다."** |
| 솔루션 1개만 만들고 넘어감 | 대안 2개 이상 규칙을 강제한다. 대안이 있어야 ICE 비교가 되고, 첫 안이 Ease에서 막힐 때 대체재가 있다 |
| 솔루션이 "개선한다"에서 멈춤 | How(UI 형태·문구·트리거 시점)까지 서술한다. "어떻게(How)까지 적어주세요" |
| Variant를 여러 축으로 변형 | 단일 축 원칙. 축이 여러 개면 별도 가설로 쪼갠다. 이날은 Variant를 만들지 않는다 |
| Rationale에 "고객에게 좋을 것 같아서" | 출처가 붙지 않은 문장은 근거가 아니다. 최소 경쟁사 스크린샷 1장을 요구한다 |
| Curiosity Gap을 낚시로 사용 | 질문의 답이 같은 화면에 없으면 Store 단계가 손상된다. 클릭률은 오르고 이탈률도 오른다 |
