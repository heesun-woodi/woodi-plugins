# 화자 이름 매핑 프롬프트

## 핵심 원칙 — LLM은 "표"만 만들고, 치환은 코드가 한다

LLM에게 transcript 전체를 다시 쓰게 하면서 화자 이름을 바꾸라고 하면,
매번 조금씩 문장이 변형되어 **원문 보존 원칙이 깨진다**. 긴 회의일수록 심하다.

그래서 LLM의 출력은 **매핑 표(JSON) 하나**로 제한하고,
치환은 `transcript_build.py --speaker-map` 이 결정적으로 수행한다.

## 프롬프트

```
아래는 회의 transcript에서 각 화자의 발화를 발췌한 것이다.
각 화자 라벨이 실제로 누구인지 판별하라.

[판단 근거로 쓸 것]
- 자기소개: "저는 ~입니다", "~팀의 ~입니다"
- 호명: "~님", "~대표님 어떻게 생각하세요"
- 역할 단서: 진행자/발표자/의사결정자의 말투와 위치
- 아래 참석자 후보 명단

[규칙]
- 후보 명단에 없는 이름을 만들어내지 않는다
- 근거가 약하면 confidence를 "low"로 준다. 모르면 name을 null로 둔다
- 한국어 회의는 같은 사람이 여러 화자로 과분리되는 경우가 잦다.
  동일 인물로 판단되면 merge_into 에 대표 라벨을 적는다 (근거 필수)

[출력 — JSON만, 설명 없이]
{
  "1": {"name": "홍길동", "confidence": "high", "evidence": "00:02:14 '제가 진행하겠습니다' + 후보 명단"},
  "2": {"name": "이팀장", "confidence": "low",  "evidence": "00:15:03에서 '대표님'으로 호명됨"},
  "3": {"name": null, "confidence": "low", "evidence": "발화 3회, 판단 근거 없음"},
  "4": {"merge_into": "2", "confidence": "high", "evidence": "말투·주제가 화자2와 동일, 구간만 다름"}
}

[참석자 후보]
{attendees}

[화자별 발췌]
{samples}
```

## 후보 명단(attendees) 만드는 법 — 정확도가 여기서 갈린다

우선순위대로 모아서 넣는다:

1. **캘린더 참석자** — 회의 시각으로 Google Calendar 일정을 찾아 참석자 이름/이메일을 가져온다. 가장 강력한 단서다.
2. 파일명에 들어간 고객사·회의명
3. 프로젝트 폴더의 최근 회의록에 등장한 참석자
4. 용어집(`glossary/`)의 인명

## 발췌(samples) 만드는 법

화자별로 **처음 3개 + 중간 2개** 발화 정도면 충분하다. 전체를 넣으면 비용만 늘고
"lost in the middle" 로 오히려 정확도가 떨어진다. 자기소개는 대부분 앞부분에 나온다.

## 사용자 정정 시

진행자가 "화자2는 이팀장이 아니라 박팀장이야" 라고 정정하면
**transcript.md · 회의록.md · Google Docs 공유본을 모두 갱신**해야 한다.
매핑 표(JSON)를 고치고 스크립트를 다시 돌리면 transcript는 결정적으로 재생성된다.
