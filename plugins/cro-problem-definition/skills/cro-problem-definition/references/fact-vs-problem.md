# 현상(Fact) vs 문제(Problem) · 고객 문제 문장 작성 규칙

> 출처: CRO 방법론 KB `02_problem-definition.md` §1~2 / `03a` §2 코칭 포인트 / `pd-output-contract.md` v2.0 §4(정본)
> STEP 1(Fact 기록)과 STEP 4(문제정의 리스트 후보)에서 쓴다.

---

## 1. 현상 vs 문제 — 판별 테스트 하나

> **"이 문장에서 솔루션이 자동으로 따라 나오는가?"**
> **나오면 아직 현상이다.**

| | ✗ 현상 기술 | ✓ 문제 정의 |
|---|---|---|
| 문장 | "상세페이지 이탈률이 높다" | "옵션이 너무 많고 복잡해서(원인), 고객이 구매 결정을 미루거나 포기한다(문제)" |
| 왜 | 해결책이 막막하다. "이탈률을 낮추자"는 구호만 남는다 | "옵션을 단순화하자"는 구체적 솔루션이 바로 도출된다 |

현상을 버리는 게 아니다. **현상은 근거로 쓴다.** 문제정의 리스트에는 두 층이 다 들어간다.

### Fact 층 / Problem 층 2층 구조

| 층 | 정의 | 예 | 기록 위치 |
|---|---|---|---|
| **Fact 층** | 관측된 객관적 사실. 검증 가능한 형태 | "본문 스크롤 30/50/70% 지점에 CTA 배너 없음 — 스크린샷 검증 완료" | **T1 (STEP 1)** |
| **Problem 층** | 그 Fact가 고객에게 만들어내는 경험 | "고객은 이 정보 입력 대화에서 앞으로 얼마나 더 남았는지 몰라, 끝이 안 보인다고 느낀다" | **T4 (STEP 5)** |

두 층을 섞지 않는다. STEP 1에서는 Fact만, STEP 5에서는 Problem만 쓴다.

### 현상 → 문제로 고쳐 쓰는 법

참가자(또는 스스로)가 현상을 썼을 때 되묻는 질문 하나:

> **"그래서 고객이 무엇을 못 하고 있나요?"**

그 답이 문제다.

- 현상: "진행 단계 표시가 없다" → 솔루션("표시를 넣자")이 바로 나온다 ❌
- 문제: "고객은 이 정보 입력 대화에서 앞으로 얼마나 더 남았는지 몰라, 끝이 안 보인다고 느껴
  중간에 답장을 멈춘다" ✅

## 2. 고객 문제 문장 작성 규칙 (정본 — 계약 §4)

문제는 **공급자 언어가 아니라 고객 관점 언어**로 쓴다.

| ✗ 공급자/표면 | ✓ 고객 관점 |
|---|---|
| "CTA 버튼이 작다" | "고객이 다음 단계 버튼을 찾기 어렵다" |
| "전환율이 낮다" | "고객은 가격을 알 수 없어서 살지 말지 판단을 못 한다" |
| "인라인 CTA가 없다" | "고객은 글을 다 읽었는데 물어볼 수 있는 문이 어디에도 안 보인다고 느낀다" |

### 정본 문장 형식 (계약 §4)

```
고객은 이 [화면/상황]에서 이런 [문제]를 [못 한다 / 모른다 / 느낀다]
```

### 규칙 3가지

| # | 규칙 | 설명 |
|---|---|---|
| 1 | **주어는 사람(고객)이다** | 화면·버튼·지표가 주어면 그건 Fact지 문제가 아니다. "CTA가 작다"(✗) → "고객은 다음에 뭘 눌러야 할지 못 찾는다"(✓) |
| 2 | **솔루션 역기술 금지** | "진행률 표시를 추가해야 한다"는 솔루션이지 문제가 아니다. 솔루션을 뒤집어 문제처럼 쓴 문장("○○가 없다")도 마찬가지다. 판별 질문: *"이 문장에서 솔루션이 자동으로 나오는가?"* 나오면 *"그래서 고객이 무엇을 못 하고 있나?"*로 한 번 더 내려가 다시 쓴다 |
| 3 | **근거 ID 없는 추측 서술 금지** | 확정 전사(T1)나 정성 근거에 없는 감정·수치·발화를 지어내지 않는다. 모든 문장은 근거 ID(Fact ID·체크리스트 항목ID)를 단다. 근거 없는 문장은 삭제한다 |

> **왜 3인칭 금지 규칙이 없는가**: 이전 버전(v1.x)에는 "1인칭으로 쓴다, 3인칭 추측형 금지"라는
> 규칙이 있었다. v2.0 계약은 문장의 주어를 처음부터 **고객**(3인칭)으로 고정하므로 이 규칙은
> 모순이 되어 삭제한다. 대신 3인칭 서술이 추측으로 흐르지 않도록 **근거 ID를 강제**하는 것으로
> 대체한다 — "고객은 ~할 것이다"가 위험한 게 아니라, 근거 없이 "고객은 ~할 것이다"가 위험하다.

### 권장 문형

```
고객은 [화면/상황]에서 [문제]를 [못 한다 / 모른다 / 느낀다].
```

서술을 길게 쓸 때 순서:
**고객이 이 화면에 온 이유 → 겪은 경험 → 막힌 지점 → 그래서 취하는 행동(이탈 등)**

### 예시 (자사 사례 — 형식만 고객 주어로 갱신)

> "CRO에 관심이 있어 이 블로그를 찾아온 고객은, 글은 유익하고 전문성도 느끼지만 다 읽고 나서
> '그래서 이제 뭘 해야 하지?'라는 질문에 답을 얻지 못한다. 직접 물어보고 싶어도 이 글 안에는
> 다음 행동으로 가는 문이 하나도 보이지 않는다고 느껴, 결국 뒤로가기를 누른다."

### 자가 테스트 질문

문장을 쓰고 나서 스스로 묻는다:

1. "이 문장에서 솔루션이 자동으로 나오는가?" → 나오면 아직 현상이다.
2. "그래서 고객이 무엇을 못 하고 있나?" → 이 답이 실제 문제다.
3. "이 문장에 근거 ID가 붙어 있는가?" → 없으면 추측이다. 삭제하거나 근거를 먼저 확보한다.

## 3. "클릭하지 않았다" vs "클릭할 수 없었다"

전환율이 낮은 이유를 **"안 했다"로 단정하지 않는다.**

| 상황 | 기록 | 의미 |
|---|---|---|
| 요소가 화면에 **있는데** 안 눌렀다 | `클릭하지 않았다` | 최적화 문제 — 개선 여지가 제한적 |
| 요소가 화면에 **아예 없다 / 비활성 / 가려짐** | `클릭할 수 없었다` | **부재 문제** — 개선 여지가 훨씬 크다 |
| 해당 없음 | `-` | |

> 전환율 0.27%가 "CTA를 안 눌렀다"가 아니라 "CTA가 화면에 존재하지 않는다"이면, 이것은
> 최적화 문제가 아니라 부재 문제다. 99.73%가 "안 누른 것"이 아니라 "누를 수 없었던 것"이다.

이 구분은 **T1 6열(안 함 vs 못 함)**에 기록한다.

## 4. "무엇이 없는가"도 Fact다

STEP 1 워크스루의 핵심은 **무엇이 있는지가 아니라 무엇이 없는지**를 보는 것이다.

- 요소 상태를 `없음`으로 명시하고, 관측 사실 칸에 "○○ 요소 없음"이라고 적는다.
- "CTA가 약하다"와 "CTA가 없다"는 **완전히 다른 문제**다. 화면에 실제로 있는지 없는지를 먼저
  확정한다.
- 단, **판독이 안 되는 것**(`❓`)과 **없는 것**(`없음`)은 다르다. 확대해도 안 읽히면
  `판독불확실❓`이지 `없음`이 아니다.

## 5. 근거 강도 (근거유형 선택 기준)

| 근거 유형 | 무엇을 보나 | 강도 | T4 근거유형 값 |
|---|---|---|---|
| 정량 데이터 | 해당 구간 이탈률·전환율·행동 로그 | 강 | `관측` |
| 화면 관측(스크린샷 전사) | 요소의 유무·문구·위치 | 강 | `관측` |
| VOC / 리뷰 / CS 문의 | 사용자가 스스로 표현한 불편 | 중 | `정성(VOC·인터뷰)` |
| UT / 인터뷰 | 실제 사용자가 막히는 장면 | 강 | `정성(VOC·인터뷰)` |
| BIAS·체크리스트 진단 | 구조적으로 실패하는 항목 | 중 | `관측` |
| 화면 근거 + 정성 근거가 같은 지점 | 정량/관측과 정성이 동일 지점을 가리킴 | 강 | `관측+정성` |

> **정량과 정성이 같은 지점을 가리킬 때** 문제가 확정된다. 하나만으로 확정하면 솔루션 단계에서
> 반드시 흔들린다. 정성 근거만으로는 BIAS X나 CRO Fail을 확정하지 않는다 — 화면 전사 근거가 없으면
> △ 또는 N/A로 둔다. 자세한 처리 원칙은 `qual-evidence-guide.md` 참조.

`가설(합성)` 근거유형은 **Sprint 1~2 합성 인터뷰 도입 시 사용 예약**이다. 이번 세션에서는
나오지 않는 것이 정상이다.
