# 지표 3층 확정 가이드 — Primary·Secondary·Guardrail·측정 가능성

> 정본: `references/output-contract.md`(ed-output-contract.md v1.0) — 이 파일과 어긋나면 계약이 이깁니다. 표 열 이름·값 도메인은 계약 §3-4(E3)·§3-5(E4)가 정본이며, 이 파일은 그 판정 기준과 예시만 보강한다.

— STEP 2(지표 3층 확정 — E3·E4)에서 읽는다

---

## 1. Primary·Secondary·Guardrail 정의

타기업 세션 덱의 원문 정의다.

| 층 | 정의 |
|---|---|
| **Primary** | 실험의 성공을 측정하는 **기준 지표** |
| **Secondary** | 실험의 성공·실패 요인을 추적하기 위한 **보조 행동 지표** |
| **Guardrail** | 실험과 별도로 **망가지면 안 되는 지표** |

세 층은 역할이 다르다. Primary는 "이겼는가"를 판정하고, Secondary는 "왜 이기거나 졌는가"를 설명하고, Guardrail은 "이겼어도 실패로 봐야 하는가"를 거부한다.

## 2. Primary 선정 기준 — 정확히 1개

**Primary는 정확히 1개다.** 2개를 두는 순간 "하나는 이기고 하나는 졌을 때"의 판정 규칙이 사라지고, 사후에 이긴 쪽을 Primary라 부르는 결과 조작이 생긴다(계약 §3-4).

**선정 기준**: 문제를 겪는 고객에게 솔루션이 노출됐을 때 **가장 먼저 개선될 선행지표**.

**필수 판정 질문**:
> "문제를 겪는 고객에게 이 솔루션이 노출됐을 때 **가장 먼저 개선될 지표**인가? 최종 KPI처럼 멀리 있는 지표는 아닌가?"

답이 "아니다"면 지면과 더 가까운 선행지표로 옮긴다. Primary는 그루밍(hg)이 확정한 PSR의 R(선행지표)과 **같아야** 한다 — 다르면 정합 질문을 띄우고 확정은 사람이 한다.

### 나쁜 예 — 최종 KPI를 Primary로 두는 경우

솔루션이 노출되는 지점과 Primary 지표 사이에 여러 단계가 끼어 있으면, 그 사이의 이탈이 결과를 오염시킨다. "최종 KPI가 결국 중요하니까"라는 이유로 먼 지표를 Primary로 잡는 것이 가장 흔한 실수다.

### 해빗팩토리 예 — B축

B축 퍼널은 `open_consult → start_consult → start_info → completed_info_first → completed_info_second → completed_contract` 순서로 진행된다(정본: 골트리 노드 JSON, §6). 만약 이 실험의 솔루션이 노출되는 지점이 **상담 시작 직전(start_consult 부근)**이라면, Primary는 최종 KPI인 **계약완료율(completed_contract)**이 아니라 노출 직후 가장 먼저 개선될 **`start_info` 도달**이어야 한다. 계약완료율을 Primary로 두면 그 사이의 정보입력·견적 단계 이탈이 섞여 "솔루션이 통했는지"를 가려낼 수 없다.

## 3. Guardrail 선정 기준 — 1~2개

**필수 판정 질문**:
> "Primary가 아무리 좋아도 이 지표가 떨어지면 **실험 실패라고 말할 수 있는가**?"

답이 "아니다"면 그 지표는 Guardrail이 아니라 Secondary이거나 그냥 관찰 대상이다. Guardrail은 성공을 증명하지 않는다 — **거부권만** 갖는다.

**개수는 1~2개** — KB 06의 조견표는 비즈니스 2~3개 + 신뢰성 2~3개를 제시하지만, 이 계약(§3-4 하단, 머리말 ①)은 **총 1~2개로 좁힌다.** 실험 판정 회의에서 실제로 거부권을 행사할 수 있는 개수라는 실효성 기준이며, KB 06 대비 이 프로젝트가 운영에 맞춰 조정한 항목이다.

### 두 계열로 나눠 본다

**계열 1 — 비즈니스 훼손 감시**

| 지표 | 허용 기준 (예시) |
|---|---|
| 이탈률 | 현재 대비 +5% 이내 |
| 하위 퍼널 최종 전환율 | 현재 대비 -3% 이내 |
| 객단가(AOV) | 현재 대비 -3% 이내 |
| 취소·환불률 | 현재 대비 +2%p 이내 |
| CS 문의 수 | 현재 대비 +10% 이내 |

**계열 2 — 실험 신뢰성 감시**

| 지표 | 허용 기준 (예시) | 위반 시 의미 |
|---|---|---|
| 트래픽 배분(SRM) | 설계 split 대비 편차 없음(카이제곱 p ≥ 0.01) | 배정 로직·노출 조건 오류 |
| 페이지 로드 시간 | 현재 대비 +10% 이내 | 스크립트가 성능을 잠식 |
| JS 에러율 | 0.1% 미만 | Variant 코드 결함 |
| 노출 이벤트 수집률 | 변형 간 편차 없음 | 태깅 누락, flicker |

> 위 허용 기준 숫자는 `cro-methodology-kb/06_experiment-design.md`가 제시하는 **예시**다. 실제 허용 기준은 지면·지표 특성에 맞춰 실험담당자와 데이터 분석가가 사전에 숫자로 합의한다 — 결과를 본 뒤 기준을 옮기는 것은 판정 조작이다.

Guardrail은 비즈니스·신뢰성 두 계열에서 뽑되, 총 1~2개로 좁혀서 확정한다. 전부 담으면 "감시 목록만 길고 아무도 안 보는" 상태가 된다.

## 4. Secondary 선정 요령

Secondary의 유일한 임무는 **"왜"에 답하는 것**이다. Variant와 사용자 사이에서 실제로 일어난 상호작용만 넣는다.

**넣을 것 — 원인 추적 지표의 예**:
- 실험군별 CTA 클릭율
- 페이지 스크롤 비율
- 실험군별 구매전환율(있다면)
- 신규 노출 요소의 발급율·사용율 (예: 등급쿠폰 발급율)

**하류 지표 — 형태로 판정한다** (계약 §3-4 · DEC-011):

기준은 **분모가 무엇인가** 하나다.

| 형태 | 예 | 판정 |
|---|---|---|
| **구간 전환율** — 분모가 처치의 결과 | `상담방 오픈 → 상담 시작` | ❌ **넣지 않는다** (Secondary·Guardrail 모두) |
| **누적 전환율** — 분모가 Trigger Point | `점검신청 진입 → 상담 시작` | ✅ **넣는다 — 권장** |

- **왜 구간이 안 되는가**: 분모(`상담방 오픈`)가 이 실험의 **결과**다. 실험군이 더 많이 열면 원래 열지 않았을 **한계 사용자가 섞여**, 개선이 성공할수록 구간 비율이 **오히려 떨어진다**(선택편향). 결과를 거꾸로 읽게 된다.
- **왜 누적은 되는가**: 분모가 Primary와 같아 두 군이 **같은 모집단 위에서** 비교된다. 표본도 판정도 오염되지 않는다.
- **몇 단계까지 볼지는 선택이다** — 노출 지점 기준 누적이기만 하면 `→ 상담 시작`도 `→ 1차 정보 입력`도 정상이다. 더 내려갈수록 신호가 옅어지는 트레이드오프만 명시한다.

| 그런 생각이 든다면 | 실제로는 |
|---|---|
| 하류가 이어졌는지 보고 싶다 | **누적 전환율 Secondary** — 분모를 Trigger Point로 고정 |
| 최종 매출 임팩트가 궁금하다 | **Uplift 시뮬레이션(hg 소관)** — 실험 지표가 아니라 사후 추정 대상 |
| 다음 지면이 진짜 병목인 것 같다 | **다음 실험의 문제영역 후보** — 이번 실험의 지표가 아니다 |

> **v1.1까지는 "다음 퍼널 단계는 Secondary에 넣지 말고 Guardrail로"였다.** 그 서술이 *구간*과 *누적*을 구분하지 않아 누적 퍼널까지 함께 막고, 하류 관심사를 Guardrail로 떠넘겨 2관문에 걸리게 만들었다 (DEC-011로 개정).

가설에 담긴 **중간 목표**는 반드시 Secondary로 측정한다 — 실패했을 때 "중간 목표조차 안 올랐다"와 "올랐는데 안 이어졌다"를 구분하기 위해서다.

## 5. 측정 가능성 점검 — E4와 일치

E3에서 확정한 전 지표(Primary·Secondary·Guardrail 전부, 층마다 1행씩 — 누락 금지)를 대상으로, 지금 실제로 측정되는지를 점검한다. 이 점검이 계약 §3-5(E4)다.

### 태깅 여부 확인 방법 — Amplitude 택소노미 실쿼리

`측정 중` / `미태깅` / `확인 불가` 세 값 중 하나로 판정하며, **추정·보간하지 않는다.** 판정 근거는 Amplitude MCP 실쿼리로 확인한다:

- 이벤트명이 택소노미에 존재하는지 조회
- 최근 기간 내 해당 이벤트의 실제 발생 여부 조회
- 필요한 프로퍼티(분모·분기 조건)가 함께 수집되는지 조회

조회조건(이벤트명·기간·필터)은 반드시 근거 열에 남긴다. MCP 미연결·권한 문제로 조회가 안 되면 멈추지 않고 `확인 불가` + `코치 확인 필요`로 두고 진행한다 — 이것도 정상 값이다(계약 §3-5).

### 미태깅 지표 — 태깅 요청 명세 양식

미태깅 판정이 나오면 **아래 4항목**을 채워야 통과다. 항목이 빠진 채 "나중에 태깅하면 됨"으로 넘어가지 않는다.

| 항목 | 내용 |
|---|---|
| 이벤트명 | 신규 또는 수정할 이벤트명 (제안 이벤트명이면 `{제안 이벤트명 — 미생성}`으로 표기) |
| trigger 조건 | 어떤 사용자 행동에서 이 이벤트가 발생해야 하는가 |
| 프로퍼티 | 분모·분기 판정에 필요한 속성(dimension) |
| 요청 대상 | 태깅을 실제로 구현할 담당(보통 개발팀) |

> 조치 기한은 이 명세 안이 아니라 **E4 표의 별도 열**이다(계약 §3-5) — `실험 시작 전` 고정 + 구체 날짜가 있으면 병기한다.

### 덱의 예시

> 모니터링이 필요한 지표 중 현재 트래킹하지 않는 이벤트가 있다면 실험 시작 전에 이벤트 태깅이 필요하다. 예: 등급쿠폰 발급 이벤트(`click_coupon_membership`) 추가 태깅.

이처럼 Secondary 지표 하나가 아직 이벤트로 존재하지 않을 수 있다 — 그 자리에 위 5항목 명세를 채워 넣는 것이 이 STEP의 산출물이다.

### 운영 분기가 있는 Variant

고객 상태에 따라 문구가 자동으로 갈리는 Variant는 **분기별로 지표를 조회할 수 있는지**를 별도 행으로 점검한다. 분기별 수치가 안 나오면 결과 해석이 막힌다.

**조회가 가능하다고 확인되면, 그 분기는 E6 `판정 군 수`에 포함된다** (계약 §7-17 · DEC-011). **분기별 수치를 보겠다고 선언한 순간 그 분기가 판정 단위**이며, 무작위 배정 여부와 무관하다 — "탐색용이라 판정에 쓰지 않는다"는 이름표는 표본 산정의 면제 사유가 아니다. 분기별 판정에는 다중비교 보정이 붙고, **기간 병목은 가장 작은 분기**가 정한다.

## 6. 해빗팩토리 이벤트 예시 — A축/B축 퍼널

E3의 "이벤트 → 이벤트 경로" 열을 채울 때 참고할 두 축의 이벤트 체인이다. **정본은 `data/goal-tree-nodes.json`(골트리 노드 JSON)** — 아래는 순서 감각을 잡기 위한 이벤트명 나열이며, 실측 전환율·트래픽 수치는 담지 않는다.

**A축 (상담방 오픈 전)**:
```
mydata_completed_ins_result → inspection_view_inspection → start_inspection → open_consult
```

**B축 (상담방 오픈 후)**:
```
open_consult → start_consult → start_info → completed_info_first → completed_info_second → completed_contract
```

지표의 분모(=E5의 Trigger Point)와 분자를 이 체인 위의 두 지점으로 정의하면 "이벤트 → 이벤트 경로" 표기가 된다. 실제 baseline 값·일 UV·최신 노드 구성이 이 나열과 다르면 골트리 노드 JSON이 우선한다 — 충돌 시 `코치 확인 필요`로 남긴다(계약 §7-10).
