# 실험설계서 작성 가이드 — 왜 구체적이어야 하는가·항목·형식

> 정본: `references/output-contract.md`(ed-output-contract.md v1.0) — 이 파일과 어긋나면 계약이 이깁니다.

— STEP 0 진입 시(인테이크 전 노션 문서 구조 파악), 참가자에게 "왜 이렇게까지 자세히 써야 하는가"를 설명하거나 노션 섹션 매핑표(§2)를 확인할 때 읽는다

---

## 1. 실험설계서가 왜 구체적이어야 하는가

### 1-1. 나쁜 예 — 성긴 설계서

> "로그인 화면 문구를 매력적으로 바꾸면 로그인을 많이 할 것이다"
> 배경: "상무님 의견"
> KPI: 로그인율, 구매전환율

문장 하나, 근거 한 줄, 지표 이름만 있는 설계서다. 이 상태로 협업 채널에 공유하면 답이 없어 진행이 멈춘다.

### 1-2. 공유 즉시 쏟아지는 질문 — 타부서 질문 공세

성긴 설계서를 공유한 순간 실제로 돌아오는 질문들이다. 이 세션의 일은 **이 질문들에 대한 답을 미리 준비하는 것**이다.

| 질문하는 쪽 | 실제로 나오는 질문 | 답을 만드는 표(계약 §1) |
|---|---|---|
| 데이터 분석 | "이 실험의 목표 지표는 무엇인가요? 측정하려면 추가로 태깅해야 할 이벤트가 있나요?" | E3 · E4 |
| 데이터 분석 | "이 가설의 근거가 뭔가요? 얼마나 개선돼야 실험군 성공인가요? 몇 명이 필요한가요?" | E6 · E7 |
| 서비스 기획 | "어떤 사용자에게 실험하는 거죠? 전체 사용자한테 다 하는 건가요?" | E5 |
| 개발 | "실험 화면 구현은 누가 어떻게 하나요? 기능 배포가 필요한 게 있나요?" | E2 |
| 마케팅 | "다음 프로모션이랑 실험 기간이 겹치지 않나요?" | E7 |

질문 하나하나가 설계서의 빈칸이다. 빈칸을 세션 중에 채우면, 실제 공유 시점에는 같은 질문이 나오지 않는다.

### 1-3. 좋은 예 — 구조를 갖춘 설계서

> **실험 가설**: "비로그인 사용자가 이벤트/쿠폰 화면 진입 시 '등급혜택'을 강조하는 문구를 노출하여 로그인을 유도하면 로그인율이 5% 증가할 것이다."
> **배경**: 데이터 분석 결과, 비로그인 사용자 구매전환율이 로그인 대비 7%p 낮고 전체 유입의 30%를 차지 — 비로그인을 로그인시키면 구매전환율 상승 가능.
> **실험 목표**: Primary = event page → 로그인완료(baseline 12.5%) / Secondary = 실험군별 CTA 클릭율 / Guardrail = 사이트 전체 일평균 구매전환율
> **실험 타겟**: 타겟 지면 = 이벤트/쿠폰 페이지 / 타겟 코호트 = 비로그인 사용자
> **실험 설계**: 대조군(50%) 변화 없음 / 실험군(50%) 로그인 유도 문구·CTA 변경
> **실험 기간**: 총 12일(필요 최소 트래픽 1,200 UV)

> (위 수치는 타기업 세션 덱 원문의 예시이며, 해빗팩토리 실제 값이 아닙니다. 실측 수치는 §5의 출처 경로를 참조하세요.)

같은 가설이라도 이렇게 쓰면 "누가 봐도 같은 그림"이 된다 — 이것이 그루밍(hg)과 실험설계 구체화(ed)의 경계다: 그루밍이 **설득 준비**라면 실험설계는 **세팅 준비**다.

## 2. 실험설계서 필수 항목 — 노션 템플릿 섹션 매핑

타기업 세션 덱이 제시하는 필수 항목은 5가지다. 해빗팩토리 노션 `가설 리스트_CRO` DB의 실험설계서 템플릿에서는 이 항목들이 1장~3장의 섹션으로 나뉘어 있고, 이 스킬(`cro-experiment-design`)이 채우는 표(E-ID)와 정확히 대응한다. 아래 표는 계약 §3-9(E8a 노션 갱신 블록)의 매핑과 일치한다 — 어긋나면 계약이 이긴다.

| # | 덱의 필수 항목 | 노션 섹션 | 채우는 표(E-ID) | 비고 |
|---|---|---|---|---|
| 1 | 실험 가설 | `1-1) PSR 가설` | — | **그루밍(hg) 완료분** — 이 세션은 재확정하지 않는다 |
| 2 | 실험 배경(정량/정성 근거) | `1-2) 문제 정의 및 핵심 근거` | — | 그루밍 완료분 |
| 3 | 실험 목표(측정 지표) — Primary/Secondary/Guardrail | `1-4) 실험 지표 (Result)` | **E3** | 이 세션에서 확정 |
| 3-부속 | 태깅 검토 | `1-4)` 하위 (토글) 추가 이벤트 태깅 검토 | **E4** | 미태깅 지표의 태깅 요청 명세 |
| 3-요약 | (실험 세팅 요약) | `1-5) 실험 세팅` | E5+E6 요약 | Target Audience·타겟 지면·Trigger Point·예상 기간 |
| 5(보강) | 실험군 시안·변경 화면 명세 | `1-3) 솔루션 설명 및 근거` (보강분만) | E2의 4·5행 | 그루밍 착지분을 **덮어쓰지 않는다** — 추가·정정분만 |
| 5-1 | 실험 타겟 지면 & 코호트 | `3-1) 타겟 오디언스` | **E5** | |
| 4 | 필요 샘플사이즈 / 실험 기간 계산 | `3-2) 최소 필요 실험 기간` | **E6** | 입력값·공식·결과·실현성 판정 4단 구조 |
| 5-2 | 실험군 설계(대조/실험군, Variant) | `3-3) 실험 설계` | **E2** | + 「실험 판정·종료 기준」 신설 소절(E7 일부) |
| 5-3 | 지면 구현·트래픽 분배 | `3-4) 기능 구현` | **E7** | 분배 비율·실험 대상 비중·노출 방법 |

**읽는 법**: 1·2번 항목(가설·배경)은 이미 그루밍에서 끝난 재료다 — 이 세션은 손대지 않고 그대로 옮겨 쓰기만 한다. 3~5번 항목이 실제로 이 세션에서 새로 구체화하는 영역이다.

> 참가자 노션 페이지가 템플릿과 다르면(예: `3-4-1) Primary 지표`, `3-5) 실행 순서` 같은 변형) **페이지의 실제 섹션 제목을 기준**으로 매핑하고, 차이를 보고한다(계약 §3-9).

## 3. 가설 형식과 배경 작성법

### 3-1. 가설 형식

타기업 덱이 제시하는 실험 가설의 기본 형식은 다음과 같다.

> **"AA를 BB로 바꾸면 XX지표가 YY와 같이 바뀔 것이다"**

이 형식은 "무엇을(AA) 무엇으로(BB) 바꿔서 어떤 지표(XX)가 얼마나(YY) 바뀌는가"를 한 문장에 압축한다. 해빗팩토리는 이미 그루밍 단계에서 PSR 형식(`[영역/시점]에서 [문제]를 느끼는 [세그먼트]에게 [솔루션 핵심가치]를 [솔루션 형태]로 제공하면 [결과지표]가 [Baseline→Target] 개선될 것이다`)으로 확정한 가설을 입력으로 받는다. AA→BB 형식은 **PSR 문장이 실제로 "무엇을 무엇으로 바꾸는" 실험인지를 배경 서술에서 다시 한번 쉬운 말로 점검하는 용도**로 쓰면 된다 — PSR 문장 자체를 이 형식으로 다시 쓰거나 대체하지 않는다.

### 3-2. 배경(정량/정성) 작성법

배경은 "왜 이 가설을 실험하는가"를 데이터와 사용자 목소리로 뒷받침하는 자리다. 정량과 정성을 함께 쓴다.

**정량 근거** — 현재 퍼널 수치를 나열하고, 그 수치들이 어떻게 연결돼 목표 지표 개선으로 이어지는지 논리를 한 줄로 잇는다.

> (타기업 예시 — 가상 수치) 일평균 유입 중 비로그인 30% / 비로그인 구매전환율 1%(로그인 시 8%) / 비로그인의 로그인 성공율 10% / 로그인 시 구매전환율 15% → "로그인율이 5% 증가하면 구매전환율이 1% 상승할 수 있다"

**정성 근거** — 인터뷰·UT에서 나온 발화를 인용해 "왜 사용자가 그 행동을 안 하는지"를 설명한다.

> (타기업 예시) 인터뷰: "로그인하면 등급 할인 쿠폰이 있는지 처음엔 몰랐다" → 등급 쿠폰 혜택을 노출하면 로그인율이 오를 것으로 기대

해빗팩토리에서 배경에 쓸 실측 수치·인터뷰 인용은 이 세션에서 새로 만들지 않는다. 그루밍(hg) 착지분(노션 `1-2`·`2-1`·`2-2`)을 그대로 가져오고, 추가 확인이 필요하면 출처만 안내한다 — 골트리 노드·이벤트는 `data/goal-tree-nodes.json`, 잔여 전환율·인원수는 `habitfactory-cro-ssot/30_deliverables/problem-areas.md`, 그 외 실쿼리는 Amplitude MCP.

## 4. 영역별 산출물 · 담당자/협업자

타기업 덱의 표를 해빗팩토리 역할에 맞춰 옮긴 것이다. `실험담당자`는 이 세션의 **참가자(해빗팩토리 PM·기획자)**를 가리킨다. 스킬은 시안·코드를 만들지 않으므로, 협업자 지점은 모두 **제작 요청 명세**로 남긴다.

| 설계서 항목 | 산출물 | 담당자 및 협업자 | 이 표(E-ID) |
|---|---|---|---|
| 가설 아이데이션·선정 | 가설 리스트 → ICE 선정 | 실험담당자(참가자) + 서비스기획자 + 개발 + 디자이너 + 데이터 분석가 | (그루밍 이전 — hb 소관) |
| 가설·배경 정리 | 가설 구체화, 배경(Problem) 정리 | 가설 최초 제안자 + 데이터 분석가 + 실험담당자 | (그루밍 소관) |
| 실험 목표(P/S/G 확정) | 지표 3층 상세 + **측정을 위한 신규/수정 데이터 명세**(event·trigger·property) | 실험담당자 + 데이터 분석가 + 가설 최초 제안자 | **E3 · E4** |
| 실험 타겟 | 실험 타겟 지면 & 코호트 선정 | 실험담당자 + 서비스기획자 + 데이터 분석가 + UX/UI 디자이너 + 개발자 | **E5** |
| 실험 설계 | 실험 영역·실험군(Variant) 기획, 변경 화면 명세 | 실험담당자 + UX/UI 디자이너(시안 제작) + 개발자(구현 가능성 판정) | **E2** |
| 샘플사이즈·기간 | Primary Baseline 확인, 샘플사이즈·기간 계산 | 실험담당자 + 데이터 분석가 | **E6** |
| 지면 구현 | 대조군·실험군 시안(Low-fi/High-fi), 기능 구현 방식 | 실험담당자 + UX/UI 디자이너 + 개발자 | **E7** |

담당자·협업자는 실제 조직 상황에 맞춰 바뀔 수 있다. 핵심은 **각 항목이 실험담당자 혼자 채우는 게 아니라 협업자와 함께 확정된다**는 점이다 — E2(디자이너·개발) · E3/E4(데이터 분석가) · E7(개발)이 이 세션에서 특히 그렇다.

## 5. 실험설계서가 구체적일수록 — 효용 5가지

1. **커뮤니케이션 비용 감소** — §1-2의 질문 공세가 사전에 답변된 상태로 공유된다.
2. **역할별 업무 파악 용이** — §4 표대로 누가 무엇을 하면 되는지 바로 보인다.
3. **일정 구체화** — E6의 예상 기간·E7의 분배 계획이 일정표에 바로 얹힌다.
4. **미리 이슈 파악** — E2의 구현 가능성 초기 판정, E7의 병행 릴리즈 확인이 늦은 발견을 막는다.
5. **빠른 업무 범위 협의** — E2의 변경 화면 명세·E4의 태깅 요청 명세가 협업자에게 "이것만 보면 시작할 수 있는" 착수점이 된다.

**"모두가 당황스럽지 않게, 구체적으로 예측 가능하도록."** 완벽한 v1.0을 한 번에 만들려 하지 않는다 — 지금 적을 수 있는 항목부터 v0.1을 채우고, 이해관계자 1차 컨택 후 v1.0으로 올린다(계약 §0-1). 미확보 칸은 지우지 않고 `⚠️미정` 또는 `코치 확인 필요`로 남긴다.
