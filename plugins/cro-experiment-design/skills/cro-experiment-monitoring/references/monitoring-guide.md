# 모니터링 가이드 — 헬스 체크·중단 등급·종료 게이트·SRM

> 정본: `references/output-contract.md`(em-output-contract.md v1.0) — 이 파일과 어긋나면 계약이 이깁니다. 임계값·하드 규칙은 계약 §7, 표 열 이름은 §3(M3~M6)이 정본이며, 이 파일은 그 판정 기준의 배경과 원인 목록만 보강한다.

— M3(헬스 — 운영 안정성)·M4(진행률+피킹 게이트)·M6(이상 징후 체크리스트) 산출 시, 그리고 M5 진입 전 「지금 판정 모드로 넘어가도 되는가」를 판단할 때 읽는다.

> **v1.1 구분 (2026-09-07):** Amplitude 실험 화면의 리프트·신뢰구간·유의성 표시는 **순차검정(mSPRT)** 결과라 샘플 도달 전에 읽어도 위양성이 통제된다 — 스킬은 이 표시값을 **항상 인용**한다(출처에 `— 표시값(순차검정)`). 피킹 게이트(계약 §7-6)가 막는 것은 **스킬 자체가 고정표본 검정(z·p·CI·베이지안·WIN/LOSE)을 도달 전에 반복 계산하는 것**이다. 둘을 섞지 않는다.

## 1. 운영 안정성 관점 — 왜 런칭 직후 1~2일에 집중하는가

우디 덱의 원칙: 런칭 후 **1~2일은 실험의 성패가 아니라 유효성 자체가 결정되는 구간**이다. 이 구간에 사람이 직접 확인해야 하는 것은 세 가지뿐이다 — ① variant 시안이 실제로 의도대로 노출되는지 사람 눈으로 확인 ② variant별 트래픽의 일자·시간대 추이에 스파이크나 다운이 없는지 ③ 지표 이벤트가 실제로 수집되고 있는지(0건 지표가 없는지). 이 세 가지는 "판정"이 아니라 "확인"이라, 런칭 직후부터 매일 봐도 무방하다.

## 2. 확인 vs 판정 — 절대 섞지 않는다

| 구분 | 실험 진행 중 봐도 되는 것 (확인) | 실험 진행 중 보면 안 되는 것 (판정) |
|---|---|---|
| 데이터 유입 | 이벤트가 들어오는가, 0건인 지표는 없는가 | — |
| 배분 | Control/Variant 배분 비율이 설계대로인가(SRM) | — |
| 가드레일 | **장애 수준** 훼손이 있는가 | 몇 % 나빠졌는지로 승패 판단 |
| Primary | (기록되고 있는지만) | 지금 이기고 있는가 / 지금 끝낼까 |

매일 보는 것은 이 표의 "확인" 칸 세 가지뿐이다. 헬스 대시보드와 결과 대시보드를 분리하고 결과 쪽은 종료 전까지 열지 않는 운영이 의지력보다 강하다. (KB08 L20-30 · 세션 블록 C-1)

## 3. No Peeking — 왜 헬스와 판정을 분리하는가

중간에 결과를 들여다보고 그때그때 판정하려는 행위는 위양성을 구조적으로 늘린다. 메커니즘은 세 가지다 — ① 다중 검정(반복 판독 횟수만큼 우연히 유의해 보이는 날이 생김) ② 정지 규칙의 편향(원하는 결과가 나온 날 멈추면 결과가 표본 크기를 정하게 됨) ③ 인지 편향(원하던 방향이면 조기 종료, 반대면 연장 — 같은 데이터에 비대칭 반응). 방증으로 임상시험 사전등록 규칙 도입 후 유의미한 긍정 효과 보고율이 급락한 사례가 있다. (KB08 L32-56 · 세션 블록 C-2)

## 4. 런칭 직후 24~48시간 헬스 체크 항목

| # | 항목 | 정상 기준 | 이상 시 |
|---|---|---|---|
| 1 | 데이터 유입 | Primary·Secondary·Guardrail 전 지표에 이벤트 유입 | 0건 지표 → 즉시 중단, 트래킹 수정 후 재시작 |
| 2 | 노출 수 | 예상 일 트래픽 대비 편차 이내(⚠️확인필요 — 코치 확정, 후보 ±30%) | 크게 미달 → 타겟팅·트리거 오류 점검 |
| 3 | 배분 비율(SRM) | 설계 비율과 실측이 유의하게 다르지 않음 | 유의한 불일치 → 즉시 중단 |
| 4 | 중복 노출 | 동일 유저가 양쪽 그룹에 잡히지 않음 | 발생 시 중단, 식별자 정책 점검 |
| 5 | 렌더링 QA | 주요 환경에서 variant가 의도대로 보임(사람이 직접) | 깨짐 발견 → 중단 후 수정 |
| 6 | 심각 가드레일 | 결제 실패율·에러율·로딩시간 급변 없음 | 급변 → 즉시 중단 |
| 7 | 지표 정의 확인 | 대시보드 지표 정의 = 설계서 정의 | 차이는 M2 매핑 표에 `차이 — {내용}(참고)`로 기록, 판정은 화면 정의 기준(v1.1) |

(KB08 L80-95)

## 5. 이후 주기 체크

| 주기 | 항목 | 산출 |
|---|---|---|
| 매일 | 데이터 유입 이상·SRM·장애 수준 가드레일 | 이상 시 알림만 |
| 주 1회 | 위 3개 + 누적 진행률(샘플 목표 대비 %) + 예상 종료일 | 로그 1줄 |
| 필요 시 | 외부 이벤트(프로모션·대형 마케팅·시즌성·앱 업데이트·장애) | 로그에 메모 |

주 1회 보고 문장은 고정한다.

> "샘플 목표 대비 진행률 XX%, 예상 종료일 M/D, 헬스 이상 {없음/있음}."

리프트를 말하지 않는다. 말하는 순간 팀 전체가 peeking을 시작한다. (KB08 L96-111 → em M4)

## 6. 중단 등급 — 즉시 / 조건부 / 유지

| 등급 | 트리거 | 조치 |
|---|---|---|
| **즉시 중단** | 핵심 전환 경로 장애·에러율 급등·개인정보 이슈 | 정지 → 원인 수정 → 데이터 폐기 후 재시작 |
| **즉시 중단** | SRM 감지·중복 노출·Primary 미수집 | 정지 → 트래킹/배분 수정 → 처음부터 재시작(부분 데이터 병합 금지) |
| **즉시 중단** | Variant 렌더링 심각 오류 | 정지 → 수정 → 재시작 |
| **조건부 중단** | 가드레일이 사전 합의한 중단 임계선을 넘어 악화 | 설계서에 미리 적어둔 임계선 도달 시 중단 |
| **유지** | Primary가 지금 지고/이기고 있다 | 아무것도 하지 않는다 — 중단 사유 아님 |
| **유지** | "그만하고 반영하자" 압력 | 사전 합의한 종료 조건을 근거로 유지 |

중단 사유는 "데이터가 잘못되고 있다"와 "사업이 다치고 있다" 둘뿐이다. "결과가 마음에 든다/안 든다"는 중단 사유가 아니다. (KB08 L112-123 → em M6)

## 7. 종료 4게이트 — 넷 다 통과해야 종료

| # | 게이트 | 확인 |
|---|---|---|
| G1 | 사전에 정한 **기간**에 도달 | 설계서의 종료 예정일 |
| G2 | 사전에 정한 **그룹당 샘플**에 도달 | 노출 수 기준(전환 수 아님) |
| G3 | 요일 주기를 최소 1회(권장 2회) 포함 | 시작·종료 요일 확인 |
| G4 | 기간 중 결과 신뢰를 훼손하는 **외부 이벤트**가 없었음 | 프로모션·장애·시즌 로그 |

G4가 깨지면 해당 구간을 제외하고 재집계하거나 재실험을 검토한다. "유의성이 나올 때까지 기다린다"도, "p<0.05가 떴으니 지금 끝내자"도 종료 사유가 아니다. (KB08 L143-152 · 세션 블록 C-3)

## 8. 조기 종료 — 허용 3가지 / 금지 3가지

| 사유 | 허용 여부 | 비고 |
|---|---|---|
| 데이터 오염·장애·SRM | ✅ 허용(=중단) | 결과를 쓰지 않고 폐기 |
| 가드레일 중단 임계선 도달 | ✅ 허용 | Loss로 기록 |
| 사전 설계된 순차 검정 규칙 도달 | ✅ 허용 | **설계 단계에서 규칙을 정해둔 경우에만** — 사후 적용은 peeking |
| Primary가 유의하게 이기고 있음 | ❌ 금지 | 대표적 위양성 생산 경로 |
| Primary가 지고 있어서 손해가 아까움 | ❌ 금지 | 노벨티·학습 효과로 초반이 왜곡될 수 있음 |
| 다음 릴리즈 일정이 급함 | ❌ 금지 | 일정은 설계 단계 제약이었어야 함 |

순차 검정은 베이지안 승자확률 기준으로 예: 95% 이상 → 채택 / 5% 이하 → 폐기 / 그 사이 → 계속(Goldilocks 방식). (KB08 L154-173)

## 9. 연장 결정 기준

| 상황 | 연장 가능 여부 | 조건 |
|---|---|---|
| 샘플 목표 미달(트래픽이 예상보다 적었다) | ✅ 연장 | 연장 종료일을 새로 못박고 그 날짜를 지킨다. 무기한 연장 금지 |
| Primary 유의·Guardrail이 유의하지 않게 나쁨 + 전환 절대 수 적음 | ✅ 연장 | 가드레일 판단용 추가 표본 확보 목적 명시 |
| Primary가 유의하지 않아서(지고 있어서) 더 돌리고 싶다 | ❌ 금지 | 결과 보고 기간을 늘리는 전형적 편향 |
| 90일을 넘길 것 같다 | ❌ 금지 | 연장이 아니라 재설계 |

연장은 1회로 제한(⚠️확인필요 — 코치 확정)하고, 종료일을 재고정하며, 연장 사유를 로그에 남긴다. (KB08 L175-184)

## 10. 종료 프로세스 흐름도

```
진행 → [모든 variant 누적 n ≥ 필요 n AND 최소 관찰 기간 AND 요일 주기 ≥1회]?
  아니오 → 지속(헬스 모드, 예상 도달일만 보고)
  예 → [SRM 정상]?  아니오 → 「실험 설계 잘못됨」 종착(리프트 불문, 결과 불사용)
     예 → [Primary stat-sig 도달]?
        예·실험군>대조군·MDE 달성·Guardrail 허용 기준 안 → WIN 종료
        예·실험군<대조군                                → LOSE 종료
        예·그 밖(MDE 미달 또는 Guardrail 허용 밖)       → INCONCLUSIVE 종료
        아니오 → [지속 판단 임계 충족 AND 지속 시 결과가 변할 수 있고 자원 trade-off 수용]?
              예 → 지속(연장, 종료일 재고정)  /  아니오 → INCONCLUSIVE 종료
```

지속 판단 임계는 stat-sig ≥ 80% ⚠️확인필요 — 코치 확정. `INCONCLUSIVE`는 하나이며 별도 이름을 붙이지 않는다(계약 §7-11). 별도 종착 「실험 설계 잘못됨」 트리거: SRM·Primary 이벤트 미수집·중복 노출/variant jumping·실험 중 배분·variant·sticky bucketing 변경 이력. (KB08 L125-186 · 세션 블록 C-4)

## 11. SRM 원인 13가지 — 중간점검 체크리스트

M6 이상 징후 15행 중 SRM·쏠림 관련 행의 재료다. 코치가 중간점검 시 그대로 훑어보는 빈도순 목록이다.

| # | 원인 |
|---|---|
| 1 | 커스텀 exposure 이벤트가 user property 할당 전에 발송되어 분석에서 exposure로 안 잡히는 타이밍 문제 |
| 2 | **실험 도중 트래픽 배분 비율 변경** — 유저가 variant 간 "점프" |
| 3 | exposure window와 analysis window 불일치 — variant별 재방문 패턴이 다르면 불공정 비교 |
| 4 | variant jumping(익명 상태·device ID 변경 등) |
| 5 | 특정 variant에서만 assignment→exposure 전환율이 다름 |
| 6 | **실험 도중 variant 추가/제거** |
| 7 | **sticky bucketing을 실행 중 켰다/껐다** |
| 8 | 특정 세그먼트(국가·OS·앱버전)에만 영향을 준 인프라 버그·업데이트 |
| 9 | 개별 유저에 대한 대량 수동 배정(Inclusions 남용)이 랜덤화를 왜곡 |
| 10 | 첫 실험에서의 계측 버그 |
| 11 | 잦은 로그아웃으로 device ID가 재생성되며 새 버케팅 인스턴스 생성 |
| 12 | exposure 이벤트 누락·불일치 |
| 13 | fallback variant에 대한 잘못된 exposure 카운팅 |

2·6·7번은 전부 "실험 중 설정을 만졌다"가 원인이다 — **실행 중에는 배분·variant 구성·sticky bucketing을 바꾸지 않는다. 바꿔야 하면 중단하고 새 실험으로 재시작한다.** 종료 게이트에 "기간 중 설정 변경 이력이 없는가"를 추가하면 G4(외부 이벤트)와 짝을 이룬다. (KB08 L406-509)

## 12. Amplitude Experiment 특이사항

Amplitude는 **sequential chi-squared test(alpha = .01)**로 variant 배분 비율의 이상 여부를 상시 감지하고 알림을 발송한다 — SRM이 뜨면 그 실험 결과는 "의심(suspect)"으로 간주해 신뢰하지 않는다(본 가이드 §6 즉시 중단 등급과 동일 처리). 두 진단 화면을 헬스 대시보드로 지정한다 — **Diagnostics card**(variant jumping 비율, assignment→exposure 퍼널)와 **Exposures without Assignments 차트**(assignment 이벤트 없이 exposure만 발생한 순유저 수 누적치, 실험 시작 전·중 상시 확인). Exposures without Assignments 증가의 3대 원인은 user ID/device ID 불일치, 계정 전환 후 `fetch()` 재호출 누락, fallback variant 수동 exposure 트래킹 오류다. (KB08 L473-513)

## 13. Monday Fixes — 실행 위생 (참고, 조직 성숙도에 맞춰 1~2개만 적용)

No peeking(본 가이드 §3)과 "작은 것에 실험 돌리지 않기"(기대 리프트가 설계 MDE에 못 미치면 애초에 테스트 대상이 아님)를 초기 조직 우선 처방으로, 확률적 자기검증과 분기별 리베이스라인(2분기 넘은 데이터 사용 금지)을 성숙 조직 처방으로 둔다. (KB08 L188-231)
